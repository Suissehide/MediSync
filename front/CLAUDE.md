# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repo layout

This directory (`front/`) is the React/Vite frontend. It is one of several apps under `MediSync/`: `back/` (Node/Fastify API, its own `CLAUDE.md`), `deploy/` (Docker compose for Postgres + app), `docs/`.

Dev server runs on port **4270** (`vite.config.ts`, `strictPort: true`) — the back's CORS config expects exactly this port, so don't let Vite fall back to another one silently.

```
src/
├── main.tsx                  # bootstrap: router, first query client, providers
├── routeTree.gen.ts           # generated by TanStackRouterVite, do not hand-edit
├── routes/                    # file-based routing (see below)
├── components/                # UI components (custom/, table/, ui/, root.layout.tsx, navbar.tsx…)
├── columns/                    # react-table column defs
├── queries/                   # TanStack Query hooks, one file per entity
├── api/                       # fetch wrappers, one file per entity (+ fetchWithAuth.ts)
├── store/                     # Zustand stores
├── hooks/                     # cross-cutting hooks (useTenantSwitch.ts, …)
├── utils/                     # permissions.ts (mirrors back/src/main/utils/permissions.ts, tested equal), tenant-context.ts, …
├── constants/                 # config.constant.ts (API URL factories, see below)
├── types/                     # shared TS types (auth.ts: User, TenantContext, …)
└── test/                      # setup.ts (vitest/jsdom), shared test harnesses
```

## Commands

- `npm run dev` — Vite dev server on port 4270.
- `npm run build` — `tsc -b` then `vite build`.
- `npm run lint` — Biome on `src`. **Not a merge gate**: it already fails on `main` (32 errors as of this writing — mostly cognitive-complexity and `any` in older components). The bar for a branch is not a green `npm run lint`, it's that the branch adds no *new* errors — compare the error count against `main` before merging, don't chase the pre-existing ones.
- `npm test` / `npm run test:watch` — Vitest (`vitest.config.ts`, jsdom, `src/test/setup.ts`).

The `@/` alias resolves to `src/` (`tsconfig.app.json` `paths`, mirrored in `vite.config.ts` and `vitest.config.ts` — the three must stay in sync, nothing enforces it automatically).

## Routing

File-based routing under `src/routes/` via `@tanstack/react-router` + `TanStackRouterVite` (`vite.config.ts`), which regenerates `routeTree.gen.ts` on every relevant file change. A `<file>.test.ts` colocated next to a route file (e.g. `$serviceId.test.ts` beside `$serviceId.tsx`, used to lock down a `beforeLoad`) is excluded from route generation by `routeFileIgnorePattern` — the plugin would otherwise try to read a `Route` export from it and fail the build.

Layout convention: a route segment starting with `_` (`_authenticated.tsx`, `_settings.tsx`) is a **pathless layout** — it wraps its children (guards, shared UI) without adding a URL segment. The tenant tree is:

```
_authenticated.tsx                          # requires a session; refreshes `authState.user` from /me
├── e/$establishmentId/
│   ├── admin.tsx                           # establishment layout: sets context WITHOUT a service
│   │   └── admin/members.tsx
│   └── s/$serviceId.tsx                    # service layout: sets context WITH a service
│       ├── _settings.tsx                   # nested under s/$serviceId, inherits its context
│       │   └── _settings/{soignant,location,thematic,planning,diagnostic-template,activity-log}.tsx
│       ├── agenda.tsx, dashboard.tsx, index.tsx, suivi.tsx
│       └── patient/{index,$patientID}.tsx
├── choose-context.tsx                      # service/establishment picker, no context of its own
└── (a dozen old top-level paths: /agenda, /settings/*, /patient/*…)  # redirect to the tenant tree, search params preserved
```

The old top-level paths (`/agenda`, `/settings/planning`, …) still exist as thin redirect files, for bookmarks and hardcoded links predating multi-tenancy — see `docs/multi-tenant/decisions-etape-2.md` for why they redirect rather than 404, and why they must forward the incoming search string explicitly (TanStack Router does not do it implicitly).

### The context is implicit, and it comes from the URL

**This is the load-bearing convention of this codebase.** There is no `establishmentId`/`serviceId` argument threaded through queries, API calls or components. Instead:

1. A route layout (`e/$establishmentId/s/$serviceId.tsx` or `e/$establishmentId/admin.tsx`) resolves the tenant from `:establishmentId`/`:serviceId` in the URL against the user's memberships, in its `beforeLoad`, and writes it to `useAuthStore` (`setContext`).
2. `constants/config.constant.ts` exposes two URL factories, `tenantApiUrl()` (establishment + service) and `establishmentApiUrl()` (establishment only), which read that same store at **call time** — not at import time, not as a prop.
3. Every `api/*.ts` and `queries/*.ts` module calls one of these two factories to build its URL.

**Never call `tenantApiUrl()` (or write a query/API module that does) from a screen that does not live under the matching layout.** It throws if no context has been set (or one without a `serviceId` for `tenantApiUrl()` specifically) — by design: a silent fallback would mean a request quietly going to the wrong establishment or service. If you're adding a screen under `admin/` and it needs a service-scoped resource, that's usually a sign the resource needs an establishment-level read endpoint (see `members.tsx`'s use of the establishment-scoped soignants read, added in this step precisely for that reason), not a reason to relax the guard.

The router precaches on hover (`defaultPreload: 'intent'` in `main.tsx`), which runs `beforeLoad` on a mere mouse-over. The layouts therefore split *resolution* (always runs, even on preload — it's cheap and has no side effect) from *side effects* (`setContext`, remembering the last visited context — gated on `!preload`, see the comment in `e/$establishmentId/s/$serviceId.tsx`). Don't remove that gate: without it, hovering a link to another service leaks that service's context into the store before you ever navigate there.

Also implicit: **nothing that lives above the two tenant layouts may mount a query observer.** An observer created there keeps whatever query client existed when it first mounted (see next section), so it could go on showing another service's data after a switch. Two different things put you in that zone, and it is worth keeping them apart:

- `__root.tsx` (the route tree's root), `_authenticated.tsx` and `components/root.layout.tsx` are **never unmounted** by a context change. `RootLayout` is rendered outside `RouterProvider` in `main.tsx`, so the router cannot touch it at all; the two route files declare no `remountDeps`, and `createRouter` in `main.tsx` deliberately declares no global `defaultRemountDeps` either — so the router re-renders them in place.
- The navbar is a different case, and the reason matters because it is the one you'll reach for when adding a widget. It does **not** survive a context change under a tenant layout: `components/dashboard.layout.tsx` renders it, and each screen renders `DashboardLayout` itself, so the navbar is unmounted *with* its screen when the layout remounts. What puts it in this zone is that it is **also** rendered outside both layouts — `routes/_authenticated/user/settings.tsx` renders `DashboardLayout` while living under `_authenticated` alone, where no remount dependency applies to anything.

What is forbidden is the **observer**, not the query: `_authenticated.tsx`'s `beforeLoad` does call `ensureQueryData` through `context.queryClient`, which subscribes nothing and survives nothing. And the one widget in that zone that reads a service API — the navbar's task panel — gates itself on a **route match** (`useMatchRoute`), never on the store's context, which still carries the last visited service on those screens. `components/navbar.test.tsx` locks both directions: absent outside the tenant layouts, present under the service layout. Any new navbar widget that reads a tenant API needs the same gate.

### Query keys deliberately do not carry the tenant

Query keys across the codebase (`useQuery({ queryKey: [...] })`) are **not** prefixed with `establishmentId`/`serviceId`. This is deliberate, not an oversight — do not "fix" it by adding a tenant prefix.

Isolation of the cache is achieved by a different mechanism, in **two halves that only work together**:

1. `hooks/useTenantSwitch.ts` builds a **brand new `QueryClient` per establishment/service pair**. Switching context swaps the whole client (adopted mid-render, not in an effect — see the long comment at the top of `useTenantQueryClient`), so the previous service's cache becomes unreachable rather than merely stale.
2. The two tenant layouts (`e/$establishmentId/s/$serviceId.tsx`, `e/$establishmentId/admin.tsx`) declare **`remountDeps: ({ params }) => params`**, which is the *only* reason a screen is unmounted and remounted when the pair changes. React Query binds an observer to its client **at construction** and never rebinds it (`useBaseQuery`: `useState(() => new Observer(client, …))`), so a screen that is merely re-rendered keeps observing the retired client. And TanStack Router renders a route's component with a React key **only** when a remount dependency produces one — without that line, going from `/e/E/s/A/dashboard` to `/e/E/s/B/dashboard` re-renders in place and unmounts nothing.

Half 1 without half 2 means the new client is built, the old one is cleared, and the screen goes on showing the previous service's data under the new service's URL — indefinitely, without even issuing a request, since the query key is identical on both sides. `routes/_authenticated/e/$establishmentId/remontage.test.tsx` locks the pair: it mounts a screen under each layout, switches, and requires an unmount, a remount, and a request to the new tenant. If you add a third tenant layout, it needs that `remountDeps` line too — nothing adds it for you, but `src/test/layouts-de-tenant.test.ts` now refuses to let you forget it. It greps the non-comment lines of every route file under `src/routes` and requires the set of files calling `setContext` (the definition of a tenant layout) to be *exactly* the set declaring `remountDeps`, in both directions, with no list to maintain. The `setContext` match is on a word boundary, not on `.setContext`, so destructuring the store first (`const { setContext } = useAuthStore.getState()`) does not slip past it.

In-flight writes against the old client (optimistic mutations, the 5-second undo window on delete) are also handled in `useTenantSwitch.ts` — they either land inertly on the retired client or bail out if the tenant pair changed since they were scheduled.

If you add a new query, **you don't have to do anything** for tenant isolation — no prefix, no manual invalidation on switch. If you're tempted to prefix a key "to be extra safe": don't. Two concurrent isolation mechanisms, one of which (key-prefixing) is inevitably incomplete (eighty keys is eighty chances to miss one), are worth less than one that is actually total. See `docs/multi-tenant/decisions-etape-2.md` for the incident that led here (§ vidage vs client neuf).

`src/test/lecture-directe-du-cache.test.ts` is a repo-wide grep-style test, and it guards **reads only** (`getQueryData`/`getQueriesData`): the one place a raw read is allowed outside `useTenantSwitch.ts` is `queries/useSlot.ts`, and anything else fails the test. It does **not** watch `setQueryData` — writing to the cache directly is the normal, unguarded way React Query does optimistic updates, and about ten `queries/*.ts` modules do it legitimately for their own mutations; that's not the risk this mechanism defends against. What needs guarding is **restoring** a snapshot taken before a switch (the failure mode in `docs/multi-tenant/decisions-etape-2.md`, D8/D13: a stale snapshot written back after the tenant has changed). That path is closed by the type system, not the test: `TenantSnapshot` (`useTenantSwitch.ts`) is deliberately opaque, so a snapshot can only be produced by `snapshotForTenant` and only ever applied by `restoreForTenant`, which checks the tenant pair before writing it back — a snapshot can't be forged, read out, or replayed by hand. The grep test's job is narrower: stopping a new optimistic mutation from reinventing that photograph-and-restore pattern by hand with a raw `getQueryData`, which is the one way to end up with an unguarded snapshot in the first place.

## Persisted (Zustand) stores and the tenant

Some Zustand stores use `zustand/middleware`'s `persist` with a storage backend from `store/scoped-storage.ts`, which namespaces the `localStorage` key by the current `serviceId` (`scopedStorageName`). A store scoped this way needs its drawer switched **and rehydrated** on every context change — `persist` only reads disk once, at module load — via `rehydratePersistedStores()` (`hooks/useTenantSwitch.ts`). Its one and only caller is `resetOnTenantChange()` in that same file, which is itself called only from `useTenantQueryClient`'s effect — the hook `App` mounts in `main.tsx` — and which must call it synchronously, before its first `await`, and before `resetTenantStores()` (see D10 in `docs/multi-tenant/decisions-etape-2.md` for why the order and the synchrony both matter). Route files have no part in this: `_authenticated.tsx` declares no effect at all. If you add a fifth persisted, service-scoped store, wire it into that function; if you add a store that mirrors service data in memory without persisting it (like `useSoignantStore`/`useTodoStore`), wire it into `resetTenantStores()` instead. Neither list updates itself.

## Permissions

`utils/permissions.ts` is a byte-for-byte duplicate of `back/src/main/utils/permissions.ts`; a back-side unit test asserts the two files are textually identical. Don't refactor one without the other. `useCan` (wherever it's consumed) reads the matrix against the current role(s) in context — it is unchanged by the tenant-context work in this step; a route not under `e/$establishmentId/s/$serviceId` or `e/$establishmentId/admin` isn't allowed to declare a permission-gated screen at all (enforced server-side at boot, see `back/CLAUDE.md`).

## Testing

Vitest + Testing Library, `jsdom` environment. `src/test/setup.ts` reassigns `globalThis.localStorage`/`sessionStorage` to jsdom's real implementations — this works around Node's own global Web Storage (active by default since Node 25) shadowing jsdom's; don't "simplify" this by reading `window.localStorage` instead, `window === globalThis` in this test environment so it's the same shadowed property.

Route-level `beforeLoad` logic (context resolution, redirects, the preload guard) is tested with disposable minimal routers rather than the full app tree — see the `.test.ts` files colocated with `e/$establishmentId/s/$serviceId.tsx`, `e/$establishmentId/admin.tsx`, `choose-context.tsx`.
